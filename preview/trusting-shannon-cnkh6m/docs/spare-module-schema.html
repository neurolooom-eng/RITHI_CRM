RITHI CRM · How it functions · Schema

The Spare module, table by table

Every table the eight Spare screens read and write — what each important field holds, whether you supply it or the database does, what it refuses, and where the value goes next. Read out of the database, not written by hand: the columns, types, keys, constraints, triggers and row-level policies below were introspected from a Postgres with every migration applied, and each refusal quoted below is the message the system actually raises.

You supply it Refused, or wrong, without a value from you.
Set for you The database fills it. Some are merely defaulted; where a value you send is discarded, the field says so.
Refused A guard rejects the write outright, in those words.

Why this does not just say NOT NULL

Reading “mandatory” off the column definition would be wrong in both directions here, so it is not what the middle column means.

Most NOT NULL columns in this module carry a default, so you never supply them — created_at, stage, total_qty. And several of the genuinely mandatory fields are nullable in the schema and demanded by a trigger instead: a reconciliation needs a UCN, a part, an engineer and a reason, and every one of those four columns accepts NULL as far as the table definition is concerned.

So the badge answers the question somebody actually has — must I put something here? — and the rule beside it says what enforces the answer.

1  The request

spare_requests · spare_request_lines · spare_request_engineer_log

Two tables and a log. The header holds who and what for; the lines hold which parts — and every approval, because approvals are recorded per spare, never on the request.

spare_requests

One row per request — one OR number. Raised on the Spare Requests screen by either route: against a call, or as HandStock.

41 columns PK id UNIQUE uid, or_no RLS on · 4 policies 5 triggers
uidtextyou supply
The key everything else points at. Both child tables reference it on delete cascade, so it is the handle for the whole request.
or_notextset for you
OR-YYMM-NNNN, drawn from spare_or_counters on a monthly series. Unique across the table. Immutable once assigned: “The OR number is assigned once and cannot be changed.”
or_req_datedateset for you
Stamped with the OR number and immutable by the same guard.
req_typetextoptional
The route. Call Based (the default) or HandStock. Matched by squashing every non-letter and lowercasing, so Hand Stock, hand-stock and HANDSTOCK all count; anything else is treated as Call Based. HandStock now requires NSM approval whatever the cover.
item_statustextoptional
The cover, and it decides the approval chain. Normalised to one of WGP · OGP · CMC · AMC by a trigger on insert and on any update of this column — “WARRANTY” is written as WGP. An unrecognised value is left unchanged rather than guessed at. Empty on a HandStock request, which has no machine behind it.
engineer engineer_emailtextyou supply
Who the parts are for. The email is what row-level security matches on, so a blank one costs the engineer sight of their own request. Cannot be changed once the parts have gone out — “OR … has already been dispatched.” Every permitted change is written to the log below.
ucn call_numbertextoptional
The call this is against, on the Call Based route. Empty for HandStock. There is no foreign key to the call — the UCN is carried as text and joined on by the reports.
party_name product_name serialtextoptional
Copied off the call when the request is raised, so the request still reads correctly if the machine is later transferred. Also text, also no foreign key.
handstock_reasontextoptional
Why the replenishment is being asked for. The only justification a HandStock request carries, since there is no complaint behind it.
stage statustextset for you
A rollup of the lines, not a field. The request sits at the earliest stage among its lines that is not Rejected or Dropped — so a request whose five parts are at Stores and whose sixth is still at Commercial reads Commercial. status mirrors stage, except that Stores is shown as Awaiting Dispatch. A value you write is refused.
rm_approval commercial_approval nsm_approval stores_status received_attext / timestamptzrefused here
These columns exist but you may not write them. Any update raises “Spare approvals are recorded per spare — update spare_request_lines, not the request”. They are kept in step by the rollup when a line changes. The reason is the whole design: a request is approved part by part, so a decision written at the header would be a decision nobody made about any particular part — and would skip the per-line permission checks entirely.
dc_number dispatched_by dispatched_at received_by couriertext / timestamptzset for you
Carried up from the lines when Stores send the parts. Read them here for a summary; the line rows are the record.
created_byuuidset for you
Defaults to the signed-in user and references auth.users. One of the two things that make somebody “the requester” for permission purposes; the other is a matching engineer_email.
extrajsonboptional
Whatever an import carried that has no column of its own. Never read by the approval logic.
Upstream — what feeds it The call (by ucn, no FK) · parties and the product database for the customer and machine · parts for the lines · Part Master for the cover vocabulary.
Downstream — where it goes spare_request_lines (cascade) · spare_request_engineer_log (cascade) · the RM Approval and Pending Dispatch registers.
Deleting Only an admin or the requester, and only while the request is still at RM Approval, unapproved and never received. Anything else is blocked outright — this is a quality record.

spare_request_lines

One row per part on a request. This is where the approval chain lives — twelve triggers, more than any other table in the module.

36 columns PK id UNIQUE line_uid RLS on · 3 policies 12 triggers
request_uidtextyou supply
The parent, on delete cascade. You may only insert a line against a request you are allowed to raise one on.
parttextyou supply
The catalogue string, CODE|Description. There is no foreign key to Part Master — see the note at the foot of this page, because it is the single most consequential fact about this schema.
qtynumericyou supply
Defaults to 1. Must be at least 1, and a request may carry at most 20 parts — the twenty-first line is refused, not truncated.
row_no line_uidint / textset for you
Assigned on insert and immutable thereafter: “The spare ID is assigned once and cannot be changed.” line_uid is unique and is what the stock-out and balance views join on.
rm_approval rm_by rm_attext / text / timestamptzthe RM supplies
Needs spare.approve_rm. Two further refusals, and they are the ones people meet: “You cannot approve your own spare request — it goes to your reporting manager”, and “… does not report to you, so their spare is not yours to approve”.
commercial_approval commercial_by commercial_attext / text / timestamptzCommercial supplies
Needs spare.approve_commercial. Commercial judges whether somebody is being charged, so the stage applies when the cover is AMC or OGP. Where it does not apply, the RM's own approval may write the literal value Auto-Approved — and only that value, with _by and _at left empty, because nobody decided it.
nsm_approval nsm_by nsm_attext / text / timestamptzthe NSM supplies
Needs spare.approve_nsm. The NSM judges whether the stock is warranted, which is a different question — so this stage applies to AMC, OGP or any HandStock request. A HandStock request has no machine and therefore no cover for Commercial to weigh, but it is still stock leaving the building, and it is the one route where nobody else is watching.
stores_status dc_number stock_out_no dispatch_uid courier dispatched_by dispatched_at dispatched_qtytext / numericStores supply
Needs spare.dispatch. dispatched_qty exists because a stock out may be partial: Stores can send three of five and the line stays open for the balance.
received_by received_at received_qty receipt_remarkstext / timestamptz / numericthe engineer confirms
The engineer's acknowledgement that the parts arrived. received_at is what moves the line to Received, and it outranks every other column in the ladder below except a rejection.
stage statustextset for you
Recomputed on every insert and update from the columns above, by the ladder below. A value you send is overwritten, not refused — the stage is a reading of the record, never an independent fact.
approval_datajsonboptional
The answers to the per-stage approval form, kept with the decision that used them. Writing an answer needs the permission for that stage.
reject_reason rejected_stagetexton a rejection
A rejection or a drop needs a reason — the bulk decision routine refuses without one. rejected_stage records where it died, which the stage alone cannot tell you afterwards.
The stage, exactly as the database computes it — first match wins
any of RM / Commercial / NSM reads reject→ Rejected
received_at is set→ Received
stores_status reads drop→ Dropped
stores_status reads dispatch→ Dispatched
rm_approval is not approved or auto→ RM Approval
commercial_approval is not approved or auto→ Commercial
nsm_approval is not approved or auto→ NSM
otherwise→ Stores
Upstream spare_requests (the cover and route decide which stages apply) · parts · the reporting hierarchy, which decides which RM may approve.
Downstream spare_dispatch_lines (FK, cascade) · the Stock out arm of the hand-stock balance · the rollup back onto spare_requests · Pending Dispatch and the Not-Consumed report.
Not allowed Deleting (quality record) · changing the spare ID or row number · writing an approval you lack the permission for · writing Auto-Approved where the stage genuinely applies.

2  Stock out

spare_dispatches · spare_dispatch_lines

Stores send the approved parts. A stock out is one batch to one engineer, it produces the Delivery Challan, and it is the IN side of that engineer's hand stock.

spare_dispatches

One row per stock out — one DC number, one engineer, whatever parts went in that batch.

14 columns PK id UNIQUE uid RLS on · 3 policies 2 triggers
uidtextset for you
Unique. What the line rows carry as dispatch_uid — there is no foreign key between them, the join is on this string.
dc_numbertextset for you
SO-YYMM-NNNN, from spare_dispatch_counters on a series-and-month key. This is the number printed on the challan.
engineertextyou supply
One stock out goes to one engineer. Selecting parts for two at once is refused rather than split, because the challan is a document about a single handover.
dispatched_bytextstamped
Stamped from the signed-in session, and what you send is discarded. This name is printed on a document that leaves the building with the company's mark on it, so it is not the client's to assert. Where there is no session at all — an administrative connection — a supplied value is kept, since blanking it would lose the only record of who booked the stock out.
dc_date dispatched_atdate / timestamptzset for you
Today and now by default. dc_date is the document's date; dispatched_at is when the record was made.
line_count total_qtyint / numericset for you
Totals for the batch, written when it is created. A summary, not the record — the line rows are.
courier remarks engineer_emailtextoptional
How it travelled and anything worth saying about it. The email widens who can see the row.

Downstream spare_dispatch_lines · the Delivery Challan and Declaration · the Stock out arm of handstock_balance · the Stock Out register.
Not allowed Two engineers in one batch · a quantity of zero or less · more than is left to send on a line · dispatching at all without spare.dispatch.

spare_dispatch_lines

One row per part in a batch. The row that actually puts stock in an engineer's hands.

11 columns PK id RLS on · 2 policies
line_idbigintyou supply
The request line it satisfies — a real foreign key, on delete cascade. One of the very few in this module.
dispatch_uidtextyou supply
The batch. A string join to spare_dispatches.uid, not a foreign key.
qtynumericyou supply
How many actually went in this batch, which may be fewer than were asked for. This is the quantity the balance counts, not the requested one.

3  Consumption

spare_consumption

One table, and the control point of the whole module. Everything else has a document and a second party behind it; this is the engineer saying what they fitted. So it is the movement that is capped, the one that cannot be deleted, and the one with a second, separately permissioned way in.

spare_consumption

One row per part booked against a call — either reported by the engineer on the visit, or reconciled afterwards by the Spare Coordinator.

20 columns PK id UNIQUE source_ref_key RLS on · 3 policies 4 triggers
sourcetextdefaults
The flag that decides who may write the row. Report (the default) needs calls.report or spare.dispatch; Reconciliation needs consumption.reconcile. It is also the flag an adjustment may never change.
ucn call_numbertextyou supply
The call the part went into. On a reconciliation both the presence and the existence of the UCN are checked: “No call found with UCN … — check the number”. A typo is caught here rather than becoming an orphan row.
parttextyou supply
The catalogue string again. Mandated explicitly on a reconciliation.
engineer engineer_emailtextyou supply
Whose hand stock the part came off — which is the balance that gets checked. Mandated on a reconciliation.
qtynumericyou supply
Must be more than zero, and capped at the engineer's balance: “… has 2 of PART in hand, so 5 cannot be consumed. Ask the Spare Coordinator to correct the hand stock first.” Reported lines are capped as well as reconciled ones — the engineer does not correct the stock, the coordinator does. A quantity of 0 means voided, which is why zero is refused on the way in but is a valid resting state.
remarkstexton a reconciliation
Why the spare is being booked by hand. One of the four things a reconciliation cannot be saved without.
original_qty adjusted_by adjusted_at adjustment_reasonnumeric / text / timestamptzset on adjustment
How a wrong line is corrected without being erased. The quantity changes, the original is kept beside it, and a reason is demanded — separately worded for the two cases: “say why the quantity is being adjusted” and “say why the line is being voided”. An adjustment may change only the quantity: not the call, part, engineer or source.
source_ref source_ref_keytext / textoptional
source_ref_key is generated from source_ref and carries a unique index, so re-importing the same file cannot double-book a part. Blank is exempt — the key is null and null does not collide.
recorded_by created_by created_attext / uuid / timestamptzset for you
created_by is filled from the session when you leave it empty, and is one of the things that lets you see your own row afterwards.
grir datatext / jsonboptional
The goods-receipt reference, and whatever an import carried.
Upstream The visit report (Report) · the Spare Consumption screen and the Call Report review (Reconciliation) · handstock_balance, which is what the cap is measured against · the call, which must exist.
Downstream The Consumption arm of the balance (OUT) · consumption_report · spare_usage and Spare Insights · unused_spare_report, which compares what was sent against what was used.
Never Deleted — the row is voided instead, quantity set to 0 with its original quantity, reason and author retained, and the stock returns to the engineer. A hard delete is blocked outright.

4  Out again

stock_transfers · stock_transfer_lines · material_returns

The two ways stock leaves an engineer without going into a machine. Both are capped against the same balance, and both are written once and never edited.

5  Where the balance starts

handstock_opening · spare_issue_history · spare_consumption_history · handstock_period

RITHI did not begin with empty vans. These four carry the figure the ledger starts from and the movements that happened before the system existed — kept in separate tables rather than back-dated into the live ones, so “what does the system know” and “what did we carry in” stay answerable apart.

handstock_opening

6  Not written by anybody

the counters · the derived views · the master

The last group holds no decisions. Numbers that must never be issued twice, a balance that is calculated rather than stored, and the catalogue everything else quotes.

spare_or_counters · spare_dispatch_counters · stock_transfer_counters · material_return_counters

One row per series and month. Four tables, two or three columns each, and nobody can touch any of them.

RLS on zero policies PK on the period
period seriestextsealed
YY/MM or YYMM, and for stock outs a series alongside it. The primary key, so one month's counter is one row.
last_nointsealed
The highest number handed out this month.
Why nobody can read them Row-level security is on and there are no policies. That is not an oversight — a table with RLS on and nothing granting access is closed to every signed-in user, for reading as much as for writing.
How a number is issued Only through the numbering functions, which run with the table owner's rights and do the increment and the read in one statement. Two people clicking Save at the same instant get consecutive numbers; neither can see the counter, and neither can set it.
What it produces OR-YYMM-NNNN · SO-YYMM-NNNN · ST-YYMM-NNNN · MRN-YYMM-NNNN — and each is then made immutable on its own record.

handstock_movements → handstock_balance → engineer_stock

Hand stock is derived and never stored. There is no balance column anywhere in this schema — the figure is recomputed from the movements every time it is asked for.

views, not tables 10 arms 8 source tables security invoker
handstock_movementsview · 16 colsderived
One row per movement, unioned from ten places across eight tables. Six kinds: Opening, Stock out and Transfer in are IN; Consumption, Transfer out and Return are OUT. Each row also says where it came from — Stores DC, Call, Transfer, MRN, Opening balance or Historical.
handstock_balanceview · 20 colsderived
The movements grouped by engineer and part. on_hand is everything IN minus everything OUT, and the six kinds are also published separately, so a balance that looks wrong can be read back to the movement that made it. It keeps the historical figures apart from the live ones as well (hist_net, on_hand_live) — the same reason the history tables are separate.
engineer_stockview · 3 colsderived
Engineer, part, quantity. The one every cap consults — consumption, transfers and returns all measure against this.
spare_pending_rm spare_pending_dispatch spare_stock_out_linesviewsderived
The three registers: what is waiting for an RM, what is waiting at Stores (with the requested and dispatched quantities side by side, for partial sends), and what has gone out.
consumption_report spare_usage spare_usage_rollup unused_spare_reportviewsderived
The reports. unused_spare_report is the one worth knowing about: it sets what was sent against what was consumed on the same call and names the shortfall.
The formula, in full on hand = opening + stock out + transfers in − consumed − transfers out − returns
Why derived and not stored A stored balance has to be corrected when a movement is corrected, and the two drift the first time a correction fails halfway. Deriving it means a voided consumption line returns the stock by itself, with nothing to remember to do.
What it costs Every read recomputes. That is why these views carry their own indexes and why the jit setting is turned off on this database — without it one balance query spent 3.7 seconds compiling a query that runs in 174 ms.

parts

One row per catalogue part — Part Master. Not a Spare table, but the master every one of them quotes.

17 columns UNIQUE item_detail_key RLS on · 2 policies no foreign keys
code description item_detailtextyou supply
item_detail is the CODE|Description string that every other table carries, and its normalised form is unique — the catalogue's real key.
activebooleandefaults true
An inactive part cannot be issued as a refurbished substitute. It does not stop anything else: a part fitted in 2014 is still consumed, returned and reported on.
category product purchase_costtext / numericoptional
What Spare Insights groups by — the consumable/spare split comes from category.
The fact that matters most Nothing has a foreign key to this table. Every request line, dispatch line, consumption row, transfer line, return and history row carries the CODE|Description string.
What follows from it Renaming a part is not an update to one row. Nine tables hold that string, so a rename is all of them or none — there is one routine that does it, and a half-finished rename would change an engineer's balance, because the balance groups by the part code it finds.
And why it is like that The string is what the old system carried, and the records are historical: a part that has been deleted from the catalogue must still read correctly on a ten-year-old consumption line. A foreign key would have refused the import.

Three things worth carrying away from all of this.

Approvals are recorded per part, never on the request. The header's approval columns exist, and writing to them is refused in those words. A request's stage is a reading of its lines — the earliest one still moving.

Consumption is the control point. Every other movement has a document and a second party behind it. Consumption has neither, so it is the one that is capped against the balance, the one that cannot be deleted, and the one where a correction demands a reason and keeps the original figure beside the new one.

The balance is not a number anybody wrote. It is the sum of six kinds of movement across eight tables, recomputed on every read. That is what makes a voided line return stock on its own — and it is why a part renamed in only eight of its nine tables would quietly change what an engineer is holding.
