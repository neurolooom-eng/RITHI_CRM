RITHI CRM · Service Calls · process reference

How service calls work

Three registers, one way of working them. Field, Installation and Preventive (PM) calls are raised in different ways and answer to permissions of their own, but each is numbered the same way, visited the same way, and takes its status from its latest visit entry. This page covers the nine screens under Service Calls: how each register is fed, how a request becomes a call, what a visit records and refuses, and what Pending Calls, Call Review and Customer Feedback do afterwards. Registering a direct customer call field by field is described in The Call module and is only summarised here. Read the middle column for what happens, the left for what the step reads, and the right for what the system refuses and what it demands.

Flow 1

Three call registers, side by side

The Field Call Register, Installation Calls and Preventive (PM) are one screen with three settings. Each call is stored in its own register — field, installation or PM — and the register is decided by the Call Type: a type beginning INSTALL is an installation, a type beginning PM (spaces ignored, so P M VISIT counts) is a PM call, anything else is a field call.

Each register answers to its own permissions. Since 30-Sep-2026 an installation call is edited, re-allocated, visited, cancelled and re-opened with the Installation Calls permissions, a PM call with the PM Calls permissions, and a field call with the Calls permissions. The database works out which register a call is on from its UCN and asks that register's permission.

Reads

  • Product Database — the machine, its customer and its cover
  • Party Master — the customer and their Serviceman
  • Standard Complaint master

Flow 1 · Step 01

A field call — raised by the desk or from a request

Create / register calls

A field call is registered with + New Field Call on the Field Call Register, from a request on Pending Registrations (Flow 2), or with + Field call on the Warranty Register, which opens the Field Call form. The form is filled from the masters — customer, then machine, then the cover the machine brings with it — and the Standard Complaint is picked, never typed.

This path is described step by step in The Call module. On a field call the customer must be one who owns a machine on record; a new customer can be typed only on an installation.

Restrictions & mandates

  • PolicyThe database refuses a new field call from anybody without Create / register calls.
  • Engineers open the register showing open calls only; a switch shows the closed ones. Every other role opens on all calls.

Reads

  • Warranty Register — the sale entry and each machine on it
  • INST Call on each machine line

Flow 1 · Step 02

An installation call — from the register, a request or the sale

Create installation calls (Commercial)

Three ways in: + New Installation Call on Installation Calls; an installation request registered on Pending Registrations; or the Warranty Register, where ＋ Installation calls (n) raises one for every machine on a sale entry that has none, and + Installation call raises one for a single machine.

A call raised from the sale says so before it is made: the Standard Complaint and Complaint Reported read INSTALLATION CALL, the three vigilance questions are answered NO, and the customer contact is left blank — "nobody reported this". The new UCN is then written back onto that machine's INST Call. Machines are raised one at a time, and a failure stops the run and names what was already created.

Restrictions & mandates

  • PolicyThe database refuses an installation call from anybody without Create installation calls (Commercial), whichever screen it was started from.
  • FunctionWriting the UCN back refuses "… already has installation call …, which is not replaced here" and "Call … is not an installation call for …" — the call must be this machine's, same product and serial.
  • A machine typed on a sale entry but not yet saved gets no call: there is no line to write the UCN back to.
  • A new customer may be typed on an installation only, because the machine does not exist yet.

Reads

  • The month's PM file, loaded on PM Bulk Upload
  • The latest PM call already in that month, for the default start time

Flow 1 · Step 03

A PM call — singly, or the monthly batch

Create PM callsUpload PM calls in bulk

A single PM call is registered with + New PM Call on Preventive (PM). The month's batch is loaded on PM Bulk Upload, which sits under Administration: every row becomes a PM call of type P M VISIT, and the database assigns each one its UCN and Call Number.

You choose the due month, which defaults to this one; an earlier month can be chosen to back-fill. Every call in the batch is dated the 1st of that month. The registration time starts at 00:30 with a 5-second gap between calls for a fresh month, or 10 seconds after the latest call that month already holds — and both can be changed before loading.

Restrictions & mandates

  • PolicyThe database refuses a new PM call from anybody without Create PM calls — including each row of a bulk upload.
  • PM Bulk Upload opens only for a holder of Upload PM calls in bulk.

Reads

  • The day, in India time
  • The highest number already issued that day for that type
  • The Call Type, for the type letter

Flow 1 · Step 04 · automatic

The database numbers the call

The database

UCN is year, month letter, day, type letter and a four-digit number: 26I12F0002 is the second Field call of 12-Sep-2026. Installation calls take I and PM calls P. The month letter runs A for January to L for December.

The number restarts at 0001 every day, for each type separately, and the day is India's — a call registered just after midnight carries that day's date. The day's counter starts past the highest number that day already carries, so a number once issued is never issued again.

Call Number: a call raised from a request carries the request's own key; a call with none is given the next CL number for its year, such as CL2600001.

Restrictions & mandates

  • The screens never send a UCN; the database writes one whenever a new call arrives without one.
  • Two calls registered in the same instant cannot take the same number — the day's counter is locked while it moves.

Reads

  • Roles & Permissions — the role's ticks, and any extra permissions on the person
  • Which register the call is on

Flow 1 · Step 05

What you may change on a call is four rights, not one

Edit … (all sections)Edit the complaintEdit customer & productEdit the vigilance answersEdit customer contact details

The edit permission of each register is the parent of four section permissions — the complaint, the customer and machine, the vigilance answers and the contact details. Holding the parent gives all four; a manager can be given only the parts they need.

A field you may not change is shown read-only with the reason — Needs the "Edit the complaint" permission — never hidden. Re-allocating to another engineer is a permission of its own on each register, and the engineers offered are the ones you may allot to: everyone active on the User Master for a role that sees every call, otherwise yourself and whoever reports to you.

Every change to a vigilance answer is recorded — which answer, from what, to what, and who — whoever made it, administrators included.

Restrictions & mandates

  • Trigger"RBAC: changing the complaint needs the "Edit the complaint" permission" — and the same for the customer or machine, the contact and the vigilance answers.
  • Trigger"RBAC: moving a call to another engineer needs the "Re-allocate a call to another engineer" permission".
  • The register offers no Edit on a Solved or Cancelled call, administrators included. The way back is Re-open or Restore.

Reads

  • The call's state — open, solved, re-opened or cancelled
  • Party Master and the warranty and contract registers, for the two Update buttons

Flow 1 · Step 06

What can be done to a call, and when

Each register's own permission

Visit Entry and Request Spares are offered while a call is open. Reco opens Spare Consumption to book a reconciliation against this exact call. Re-open call puts a closed call back on the open list and counts it; Close again withdraws a re-open made only to correct the call, returning it to what its last visit said without inventing a visit.

Cancel call is for a call that should not exist, and is offered only while the call is Unattended or Unsolved. It keeps the UCN and everything recorded against it, and asks why; a call that has been visited is warned that cancelling does not remove the visit or anything consumed on it. Restore call undoes it, and the cancellation stays on the record.

🏢 Update Party Details sets City and State from the Party Master; 🛡️ Update Product Details sets warranty, contract and item status as on the call's registration date. Both work on a call of any status, singly or on ticked calls.

Restrictions & mandates

  • MandateA cancellation needs a reason: "A cancellation needs a reason".
  • FunctionCancel refuses a call that is not Unattended or Unsolved, or that is re-opened, however it is asked for: "Call … is Solved: only an Unattended or Unsolved call can be cancelled" (0311).
  • FunctionRe-open refuses "Call … is not closed, so there is nothing to re-open" and "Call … is already re-opened"; Close again refuses "Call … is not re-opened — close it by entering the visit that solved it".
  • FunctionUpdate Party / Product Details are hidden while Audit Mode is ON and refused by the database then too.
  • There is no way to close an open call without a visit from these screens: enter the visit, or cancel the call.

Flow 2

From a request to a call

An engineer in the field raises a request on Request Registration; the Hotline turns it into a call on Pending Registrations. How the request form is filled — the machine names the customer — is in The Call module. This flow is what happens to a request once it is raised.

Reads

  • Product Database — the machine, by serial; its customer follows
  • Call Type master

Flow 2 · Step 01

The request is raised and given a REQID

Raise call requests

＋ New Request takes one to five calls — each a product, serial, Standard Complaint and reported problem — and every call becomes its own row sharing the REQID, which the database assigns. The register shows every request and what became of it: Pending, Registered, Mapped or Cancelled.

A request can be corrected while it is still Pending. Once it is answered — registered, mapped or cancelled — its details are frozen, because the call now carries them.

Restrictions & mandates

  • MandateProduct, Serial No and Reported Problem on every call, and an answer to Call Attended? — with the Attended Date when it is Yes.
  • The same product and serial cannot appear twice on one request.
  • Trigger"This request is already … — … cannot be changed here. The call carries these details now, so correct them on the call itself; changing the request would leave the two disagreeing about one machine."

Reads

  • Requests with no UCN that are not cancelled — all of them, not a first page
  • Open calls on the same machine (model and serial), or on the same party when the request has no serial

Flow 2 · Step 02

Pending Registrations — the Hotline's queue

Register pending (Hotline)

Every request still without a UCN, newest first, with the count in the title. The Open Calls column says how many calls are still open on that machine — Unattended, Unsolved, Report pending or re-opened — so the desk sees a repeat before raising a second call for it.

Clicking a request opens three panes, each resizable: the request; the open calls with the actions; and every call ever registered on this machine, whatever its status, because a call solved last month is often what says this is the same fault coming back.

Restrictions & mandates

  • A check that failed reads not checked, never "—": "The check for open calls failed, so it is not known whether one is pending on this serial/party. Refresh the list before registering a new call."
  • A call on a different product that merely shares the serial is not offered.
  • Without Register pending (Hotline) the queue can be read but not actioned: "Your role can view requests but not action them."

Reads

  • The open call chosen, or a UCN typed in
  • Your section permissions, if you edit the call first

Flow 2 · Step 03

Map it to a call that already exists

Register pending (Hotline)

Map beside an open call, Map this UCN for one typed in, or the UCN Number (Mapped) cell on the list. The UCN is written onto the request, it reads Mapped, and it leaves the queue.

A call on this machine may need its failure details filled in before the request is closed against it, so ✎ Edit opens that call in the third pane with the same section locks as the call registers.

Restrictions & mandates

  • A typed UCN that matches no call asks first: "No call found with UCN …. Map the request to it anyway?"
  • Editing a call here is refused where your role cannot edit that register: "Your role cannot edit this … call."

Reads

  • The request — party, product, serial, complaint, engineer, contact, dates
  • Product Database — the machine with exactly that model and serial, for its cover only

Flow 2 · Step 04

Or create the new call from it

The register's create permission

＋ Create new call opens the registration form beside the request, already filled. Party, product and serial come from the request; the Product Database fills only the cover — item status, warranty and contract — and only where one machine has exactly that model and serial. The call is allotted to the engineer who raised the request, and Person Calling reads DIRECT ENGINEER.

The complaint and breakdown dates are the day the request is about — the attended date if the call was attended, else the day it was logged — and the form says which. An installation request opens the Installation form; any other opens the Field form. On save the UCN is written back onto the request, which reads Registered.

Restrictions & mandates

  • ＋ Create new call asks the register's own create permission — "Creating this kind of call needs its register's Create permission".
  • No match fills no cover: "No machine in Product Database is … with serial … — warranty/contract not auto-filled." An ambiguous serial is not guessed at either.
  • Picking a machine on the form does not replace the requester as the engineer while the request names one.

Reads

  • The reason you type — free text, not a master list

Flow 2 · Step 05

Or cancel the request

Register pending (Hotline)

✕ Cancel request asks for a Cancel reason and an optional Note; the two are kept together as the request's cancel reason, with who did it and when. The request reads Cancelled and leaves the queue without ever becoming a call.

The reason is typed, not chosen from the call cancel reasons: withdrawing a request and cancelling a call are different acts.

Restrictions & mandates

  • MandateCancel reason * — the button stays disabled until one is typed.
  • Every request leaves the queue by one of three stated routes — mapped, registered or cancelled.

Flow 3

The visit

A visit is filed with 📝 Visit Entry on the call, in whichever register it sits. Each visit is its own row — a call visited three times keeps three — and the call's status is read from the latest one entered. Visit Reports / Service Reports is the list of all of them.

Reads

  • The call — UCN, Call Number, Call Type, complaint date
  • Call Pending Reason and Standard Complaint masters
  • The customer's CPX / ASU accessories, for the accessory serial
  • The previous visit's service report, to look at

Flow 3 · Step 01

Visit Entry — what the engineer records

File a visit on … call

UCN, Call Number, Call Type, your e-mail and the Visit Entry Date are filled in by the app. The engineer gives the Visit Date, the Visiting Service Engineer (yourself by default) and the Call Status: Solved - Report Completed, Unsolved or Solved - Report Pending.

The Service Report section: Standard Complaint, Complaint Observation, Job Done, Hour Meter Reading, Software Version, Manual Report, Add Consumption?, Accessory Serial No (CPX/ASU), Maintenance Done? and Recomended Filter Changed? — and on an installation call, Warranty Start Date?, which starts at today and can be changed.

On Solved - Report Completed the signed Manual Report is uploaded (PDF or photo, up to 10 MB, to the CallReg Drive folder), an optional Customer sign-off is offered, and the Customer feedback questions for that kind of call appear.

Restrictions & mandates

  • Mandate"Visiting Service Engineer is required — say who attended." and "Choose a Call Status."
  • Mandate"Call Pending Reason is mandatory for an unsolved call." On Solved - Report Pending it reads Report Pending.
  • "A visit cannot be dated in the future", nor "before the complaint".
  • MandateComplaint Observation, Job Done, Hour Meter Reading, Software Version, Add Consumption?, Recomended Filter Changed? — and Warranty Start Date? on an installation — whenever Update Visit Work Details? is Yes, which it always is on Solved - Report Completed.
  • Mandate"Manual Report is mandatory when the call is Solved - Report Completed — upload the signed report."
  • Mandate"Customer feedback is mandatory for a solved call." Every rating and yes/no question is answered.
  • A Solved or Cancelled call takes no Visit Entry until it is re-opened or restored.

Reads

  • Every visit row on the call, by when it was entered

Flow 3 · Step 02 · automatic

The call takes its status from its latest entry

The database

Whenever a visit is added or changed, the database reads the call's visits, takes the latest one entered — by Visit Entry Date, not Visit Date — and copies its Call Status and Visit Date onto the call. A visit dated 30-May-2026 but written up on 03-Jun-2026 therefore counts as the latest entry on 03-Jun-2026.

A call is Unattended only while it has no visit. After that the status text decides, tested in this order: anything mentioning cancel is Cancelled; unsolved is Unsolved; report pending is Report pending; anything beginning solved is Solved; anything else is Report pending.

A new visit on a re-opened call ends the re-open: the call then reads whatever that visit said.

Restrictions & mandates

  • TriggerThe status is worked out by the database and whatever a screen sends for it is discarded.
  • Unsolved is tested before Report pending, so Solved - Report Pending never reads as Solved.

Reads

  • The visiting engineer's hand stock — only what they hold is offered
  • Part Master — the list is narrowed to parts that fit the call's product, with a switch to show all

Flow 3 · Step 03

Spares used on the visit

Book spares used on a visit (any register)

Add Consumption? is Yes or None Consumed — a stated answer either way. Yes opens the spare picker over the engineer's hand stock, with quantity and the batch, goods-receipt or serial number of what was fitted. A spare left in the picker when Save Report is pressed is booked too.

The visit is saved first, then the spares, then the feedback. If the spares fail the visit stays filed and the screen says so: pressing Save Report again retries just the spares.

A reconciliation — a part fitted but never reported, booked by hand with Reco or on Call Review — is the one booking that does not need a visit, because the missing visit is why it exists.

Restrictions & mandates

  • Mandate"Add Consumption? is Yes — add the spare that was used, or set it to None Consumed."
  • Trigger"No visit has been filed on … yet, so a spare cannot be booked against it. File the visit report first — the spare is recorded on the visit it was used on."
  • TriggerNever beyond the engineer's balance: "… has … of … in hand, so … cannot be consumed. Ask the Spare Coordinator to correct the hand stock first."
  • PolicyA reconciliation needs Add consumption against a call (reconciliation); any other booking needs Book spares used on a visit.

Reads

  • Service Manuals and Technical / Service Notes — active ones only
  • Knowledge Base articles
  • The call's product, Standard Complaint and reported problem

Flow 3 · Step 04

The documents offered on the call

Anyone who can open the call

The call's view lists 📄 Supporting documents: the service manuals and the active technical notes that match the call's product, complaint or reported problem — so an accessory's manual reaches a call that names the accessory — and the Knowledge Base articles for it. A manual or note with no product set is offered on every call. The same list appears on a request while it is being raised.

Below it: the visit history, the spares requested (refused and dropped lines are not listed), the spares consumed and the customer feedback. On a solved call, a part sent and not fully booked is flagged by quantity.

Restrictions & mandates

  • A retired manual or note is never offered.
  • Where nothing matches, the panel says so rather than disappearing.
  • A read that failed says so: "an empty one here does not mean there is none".

Reads

  • Every visit, newest visit first

Flow 3 · Step 05

Visit Reports / Service Reports — one row per visit

View calls

The visit history of every call you may see, one row per visit, not per call, filtered by UCN, Call Number, Engineer or Status. Clicking a visit shows every field and its service report; 📄 Show opens the signed report in the app. Any field the engineers filled can be turned on as a column, and ⭳ Excel / ⭳ CSV download what is loaded.

Two dates, on purpose. Visit Date is when the engineer was there; Visit Entry Date is when the register was told. This screen lists by Visit Date; the call's status follows the Entry Date.

Restrictions & mandates

  • Read-only: a visit is filed and corrected from its call, not here.
  • TriggerNo visit can be deleted through the application.
  • PolicyYou see the visits on calls you may see — your own, your team's, unallotted ones, or every call for an office role.
  • A download over a partly loaded list says so, and its About sheet says what the file covers.

Flow 4

After the visit

Three screens read the calls and visits back: Pending Calls for what is still open, Call Review for whether a solved call's report can stand, and Customer Feedback for what customers said.

Reads

  • Every call not cancelled that is not Solved, plus every re-opened call — all three registers

Flow 4 · Step 01

Pending Calls — everything still open

Opened by its module tick

Four tiles count Unattended, Unsolved, Report pending and Reopened; click one to show only those. All · Field · Installation · PM chips, a chip per engineer with what they are carrying, and a search narrow it further. Clicking a call opens it in its own register.

The line under the title says whose calls you are looking at — 🌐 All calls, 👥 Your team or 🙋 Your calls. Calls are read 2,000 at a time; while more remain, every count carries a +. ⭳ Export CSV downloads what is shown.

Tick calls and Allot to an engineer to re-allocate several at once, across registers.

Restrictions & mandates

  • Each ticked call needs its own register's re-allocate permission; if any does not, nothing is moved and the screen names the calls.
  • Where the database moves fewer than were ticked: "… The other … were not changed — your role may not re-allot them."
  • An empty list means everything is closed only for a role that sees every call; anyone else is told "Nothing is pending that you can see".

Reads

  • Solved calls, not cancelled and not re-opened, whose status is not Report Pending
  • The call's visits and spares consumed
  • The attending engineer's hand stock, for Reco

Flow 4 · Step 02

Call Review — can the report stand?

Review a closed call's report (mark Report Reviewed)

A different question from the Daily Complaint Review Register: not what the failure was, but whether the engineer's report closes the call. Three panes — calls, the call, and what happened on it — with Awaiting review, Reviewed and All solved.

Three things can be done. Report Reviewed, with optional Review remarks, records that somebody has looked; there is one review per call, re-marking it overwrites, and the database stamps who and when. Reconciliation books a spare the engineer did not, off the attending engineer's hand stock, with a reason. Re-open sends the call back to the open list.

Restrictions & mandates

  • PolicyMarking a review needs Review a closed call's report, and the call must be one you may see. Without it the screen is read-only and says so.
  • MandateA Reconciliation needs the part, a quantity of at least 1 and "a reason — why it is being booked by hand"; it needs Add consumption against a call (reconciliation).
  • Re-open is offered only with the call's own register's re-open permission, and asks why.
  • A review cannot be deleted.

Reads

  • Customer feedback — taken on solved visits, or loaded from the old export
  • The calls' states, to colour each UCN

Flow 4 · Step 03

Customer Feedback — what customers told us

View feedbackRecord customer feedback on a visit

One row per feedback, one column per question. Date is the feedback's own date — for a loaded row the date its export gave it, for one taken here when it was taken — and Loaded on is when the row arrived, a separate fact. Source tells Uploaded from Entered here, with a count on each chip.

Feedback is taken on the Visit Entry of a call reported Solved - Report Completed. The questions depend on the call: installation calls are asked about start-up, packing and delivery; field and PM calls about the product's reliability, the service and its promptness; field calls also whether an advance PM was done; and every call about operating feasibility, support and remarks.

Restrictions & mandates

  • PolicyReading feedback needs View feedback or Record customer feedback on a visit; on this screen, a role that does not see every record sees the feedback of its own engineers.
  • IndexOne feedback per call, keyed on its UCN.
  • TriggerNo feedback can be deleted through the application.

Who may see what

The screen's tick opens the page; the database decides the rows. A call is visible to a holder of View calls when any of these is true:

  • The role sees every call — Hotline, NSM, Commercial, Spare Coordinator, Stores Incharge, Tally Coordinator, an administrator, or anyone holding View all data (every record).
  • You registered it, or it was filed to your desk.
  • It is allotted to you, or to somebody below you on the User Master — by reporting manager or regional manager.
  • It is allotted to nobody.

Requests follow the same rule: those you raised, those carrying your e-mail, your team's, or all of them for a role that sees every call.

The records kept

  • Two registrant columns. A call is filed to the Hotline desk whoever typed it in, and the database separately stamps the person who actually typed it from the sign-in. The two differing is a finding, not an error.
  • System columns. Every table except the number counters also records which login created and last changed each row, and when, written by the database.
  • Never deleted. Calls, visits, spare requests, consumption and feedback cannot be deleted through the application: "RECORD RETENTION: … records cannot be deleted … Use the defined status / cancel / drop workflow."
  • Two counts that both are right. Visit Reports counts visits; the Call Report counts calls, each with its latest visit. A call visited three times is three rows here and one there; an open call with no visit is none here and one there.

Not yet in place

Stated here so nobody reads this page as describing them as done.

  • The re-open reason is asked and not kept. Call Review requires a reason before Re-open, but the database's re-open does not store it; the call keeps only when it was re-opened and how many times.
