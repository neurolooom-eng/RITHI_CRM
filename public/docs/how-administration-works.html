How administration works

Who may do what, what goes in, what comes out, and how the system is set. This page covers the thirteen screens under Administration: Solved Without a Report, Tracker, Roles & Permissions, Audit Log, Bulk Uploads, Bulk Report Mapping, Data Export, Device Cache Status, PM Bulk Upload, Admin Config, Software Validation, Settings and Version History — what each is for, what you do there, what it refuses, which permission each action needs, the records it keeps and what it changes elsewhere. Read the middle column for what happens, the left for what the step reads, and the right for what the system refuses and what it demands.

Flow 1

Access and the trail — Roles & Permissions, Audit Log

Two kinds of tick. Every screen has a page key — on the matrix it is the box on the page's own row, and elsewhere it reads Open: <screen>. It opens the page and nothing else. The action keys listed under the page are what can be done there. A role can be allowed to open a page and do nothing on it, and the database asks for the action keys again whatever the screen shows.

A role whose stored list is empty is not a role with no permissions. It is "not configured", and both the application and the database then give it an Engineer's permissions. That is why the screen will not save an empty role and why a new role must start as a copy.

Reads

  • Every role's stored permission list — every signed-in user may read it
  • The master value lists, one page each under Master

Flow 1 · Step 01

Roles & Permissions — reading the matrix

Open: Roles & PermissionsManage roles & permissionsOpen the administration pages, read-only

One column per role, built-in and added. The rows are grouped under the same headings, in the same order, as the menu; each heading lists its pages, and a page opens to show its actions. ⌄ Expand all and › Collapse all open and close the lot. The screen's own line: "View is permission to open the page. The actions under it are what can be done there."

Under an open page, Everything on this page gives a ✓ / ✕ per role that ticks or unticks every action on the page and the page itself. The Master heading carries one 🗂 page per value list, each with Add / edit values in this list and Delete values from this list. The last heading, Across the system → Not tied to one page, holds View all data (every record), Export / download CSV, Open the administration pages read-only, and Save a table layout for everyone or for a role.

Restrictions & mandates

  • Without either key: "You don't have permission to manage roles."
  • With Open the administration pages, read-only alone the boxes are greyed and the foot reads "You can read this matrix but not change it."
  • PolicyChanging a role's stored list needs Manage roles & permissions.

Reads

  • The parent list — the same list the database reads

Flow 1 · Step 02

Ticks with parts — “all of the below”

Manage roles & permissions

Manage users, Edit masters, Edit sales / warranties, Edit contracts, and each call register's Edit and Report are made of smaller ticks listed under them (the ledger below names every one). Holding the parent grants every child: the child's box shows ticked, and its tooltip names the parent.

Unticking a child releases it (since v0.10.34, 02-Oct-2026). The parent is unticked and every other child it was granting is ticked in its own right, so the role loses only the box you clicked. The tooltip says so: "Granted by “…”. Unticking this unticks “…” and keeps its other items ticked." A child with several parents — Book spares used on a visit and Record customer feedback on a visit are children of all three registers' Report — is released from each one the role holds.

Four older inheritances are not drawn as ticks. All Masters opens every value list, Reports (all of them) opens every report, Service Manuals opens Technical / Service Notes, and Edit masters grants every list's Add / edit and Delete. The matrix leaves those boxes empty; the export says a role can reach a list "without a Yes against it here."

Restrictions & mandates

  • FunctionThe database grants a child to whoever holds its parent, so screens and policies test the child, never the parent.
  • Reset a person’s password is not a child of Manage users — ticking Manage users never hands it over.

Reads

  • The roles you changed since the screen loaded
  • Admin's stored list, compared with every key there is

Flow 1 · Step 03

The Admin column, and Save permissions

Manage roles & permissions

The Admin column is the only thing greyed. Its header says "Admin holds every permission — this column cannot be changed", and the page subtitle adds that a Super Admin has full access too — "which is not a role and cannot be granted here." Every other role's every box is tickable.

Save permissions writes only the roles you touched; a role nobody edited is left exactly as stored. If Admin's stored list has fallen behind the full set of keys, Save re-writes it. The result: "Saved N roles: … They apply on each user’s next action / reload." Pressed with nothing changed: "Nothing was changed, so nothing was written."

Restrictions & mandates

  • MandateA role with nothing ticked is not saved: "… would be left with NO permissions ticked. An empty role means "not configured" and falls back to the built-in defaults, which is not what unticking everything looks like it does — tick at least one, or remove the role." This refusal is the screen's alone — see Not yet in place.
  • FunctionA role whose stored list is empty is given the Engineer role's stored permissions by the database (tested).

Reads

  • The role you copy from, as it stands on screen
  • Existing role keys, to refuse a duplicate

Flow 1 · Step 04

＋ Add a role — always a copy

Manage roles & permissions

Role name builds the Key shown beneath it — lower case, letters, digits and underscores — "this is what the database stores, and it cannot be changed later." Copy permissions from picks the role to start from; copying Admin gives every key, including every value list's. Add role writes the new role at once, adds its column and says "Added “…” (…) with …'s N permissions. Untick what it should not have, then Save."

A role is never deleted from this screen: "people may be on it, and removing it would drop them to the engineer fallback without telling anybody. Untick everything it holds instead, or move its users first."

Restrictions & mandates

  • Mandate"Give the role a name." · "Choose the role to copy from — a role cannot start empty."
  • "That name has no letters or digits in it — the key is built from the name." · "A role key cannot start with a digit."
  • "… is reserved." — admin, super_admin, authenticated, anon and postgres. · "A role with the key "…" already exists."
  • The ＋ Add a role card is shown only with Manage roles & permissions.

Reads

  • The matrix as it is on screen, saved or not
  • Each role's stored list, to say where its row comes from

Flow 1 · Step 05

⭳ Export matrix

Open: Roles & Permissions

Offered to a read-only viewer as well. It downloads permission-matrix-<date>.xlsx with three sheets. Matrix: Group, Page, Route, Grants, Permission key and a Yes / No column per role — one row per grantable thing, with the page's own key as an Open the page row. Roles: Role, Key, Permissions held, and Where this row comes from — Stored in the database, Always full — not stored, and cannot be changed for Admin, or NOT CONFIGURED — showing the Engineer fallback, which is what these users actually get. How to read this: taken from, on and by, and whether the file is Saved or UNSAVED — changes made on screen and not yet saved are exported, and the file says so.

Restrictions & mandates

  • The export is recorded in the Audit Log as rbac.export.
  • It does not ask for Export / download CSV — see Not yet in place.

Reads

  • The audit log, newest first, 500 at a time
  • A copy kept on this device, shown at once and refreshed every 30 minutes while no filter is set

Flow 1 · Step 06

Audit Log — what the application recorded

Open: Audit LogView audit log

Columns: Time, User, Email, Role, Action, Target, Status, ms, Error. Filter by Action (e.g. login, call.create) and Email — both match any part — and Status (ok / error). Load more reads the next 500; ⭳ Export CSV downloads the rows loaded.

What is in it. Sign-ins, failed sign-ins and sign-outs, and the actions screens record as they happen — among them call.create, call.report, spare.request, spare.drop, rbac.save, rbac.role.add, rbac.export, tracker.add, tracker.delete, user.reset_password and report.solved_without_report — each with how long it took and any error. The database stamps the login, the email and the time; the display name and role come from the application.

The second trail. Separately, the database keeps a before-and-after copy of every row written to fifteen tables — the three call registers, visit reports, call requests, pending registrations, spare requests and their lines, spare consumption, feedback, material returns, stock transfers, training sessions, training attendance and R&R periods. A single write of more than 150 rows is kept as one event naming the table and the count. This trail is written by the database, so it cannot be bypassed, and it is never purged. It is readable by an administrator or a holder of View audit log; no screen shows it.

Retention. Audit Log rows older than the retention setting — 3,650 days unless changed — are deleted by a daily job at 00:30 UTC, where the project has scheduled jobs switched on. The Audit Mode history is a third, separate record: it is on Admin Config.

Restrictions & mandates

  • Without the key: "You don’t have permission to view the audit log."
  • PolicyReading needs an administrator or View audit log (since 02-Oct-2026; before that, administrators only).
  • PolicyNothing can change or delete an Audit Log row through the application. Any signed-in user can add one; somebody not yet signed in can add only a sign-in or failed sign-in.
  • The log is written by the application, so a write made directly to the database, not through a screen, leaves no Audit Log row.
  • The CSV needs Export / download CSV.

Flow 2

Getting data in — Bulk Uploads, Bulk Report Mapping, PM Bulk Upload

You pick the register; the register says what the file means. A Call Type sheet and a Pending Reason sheet look alike, so nothing is guessed from the headings: the register you choose stamps what the file cannot say — the list name, the call type. Every file is previewed before anything is written.

The upload keys open the screens, not the tables. Load registers in bulk and Upload PM calls in bulk add reach to nothing: every row still has to pass the write rules of the table it lands in, exactly as if it had been typed.

Reads

  • The register list, plus one upload per value list
  • The row count each register's table holds now
  • Your CSV file

Flow 2 · Step 01

Bulk Uploads — pick a register, then its file

Open: Bulk UploadsLoad registers in bulk (Bulk Uploads)

Registers are grouped Calls, Visit Reports, Spares, Quality, Masters, Master Value Lists and Cover; each shows how many rows its table holds, a note saying which export it takes, and — where it points at another register — "Load … first — these rows point at it." Choose a .csv file on the register's row.

Under Cover, Installation Warranty Start (old installation calls) loads past installations — back to 2018 — one row per call, matched on the UCN. Each row's Warranty Start Date? choice and solved date decide that machine's warranty in the Product Database exactly as an installation report does; the resulting start and end are worked out by the database, not taken from the file.

The heading row is found, not assumed to be the first, using the register's own column names — so a sheet printed with a letterhead above its headings still reads. Dates are read day-first (03/04/2026 = 3 April). A column is read month-first only where its own values prove it (a number above 12 where the month would be), and the preview then says so by name.

Restrictions & mandates

  • Without the key: "Bulk uploads need “Load registers in bulk” on Roles & Permissions."
  • PolicyEach row is written only if your own rights allow that table to be written — the key adds nothing.
  • An empty file: "That file has no rows."

Reads

  • The register's column list — each column's accepted headings, and which are required

Flow 2 · Step 02

The preview — ready, held back, kept, ignored

Load registers in bulk (Bulk Uploads)

The row shows N ready · N held back · N kept on the row (or ignored). Opened, it lists: columns set by this register, whose file value is ignored; columns read month-first; columns not kept because the register was told it does not want them; columns kept on the row — stored with the record as written, where the register keeps extras — or not loaded where it has nowhere to put them; the first eight rows held back, each with its reason; the recognised columns, required ones marked *; and the first row exactly as it will be written.

A cell a typed column cannot read — 15/13/24 as a date, two as a number — is kept with the row's extras where the register has them, rather than lost.

Restrictions & mandates

  • MandateA row missing a required column is held back and named — "row N (no …)". The ledger below lists each register's required columns.
  • Some registers hold back rows the database would refuse, by name, so the rest of the file still loads (ledger).
  • Nothing loadable: "Nothing loadable — every row is missing … Is this the right register for this file? Each register's note says which export it takes."

Reads

  • The register's matching key, where it has one

Flow 2 · Step 03

Blank cells, and what a re-load does

Load registers in bulk (Bulk Uploads)

A blank cell normally changes nothing: the column keeps what it had, or takes its default on a new row. Only the Product Database upload empties a column whose heading the file carries with a blank cell — that file is a machine's whole row, so a blank means "none". Even there, a column the register stamps and a required column are never emptied. A heading the file does not carry at all leaves its column alone, on every register.

A register with a matching key corrects on a re-load: a row whose key is already there is updated, not added again. Within one file the last row of a repeated key wins — except the WinMax opening stock, where lines sharing a part code are added together, and value lists, where rows differing only by product both stay. A register with no key adds every row again: the MRN Register and Stock Transfer Lines, each marked "⚠ No natural key: a second run adds rows rather than correcting them."

Restrictions & mandates

  • IndexA register's key needs its index on the database; without it the load stops with a message naming the key and pointing at _status.sql.

Reads

  • What the rows point at — spare requests, stock transfers, active User Master names, visits, the Standard Complaint list

Flow 2 · Step 04

⤵ Upload — prepare, confirm, write in batches

Load registers in bulk (Bulk Uploads)

Prepared first, before you are asked to confirm, so the number you approve is the number written. Spare Request Lines: each OR number is matched to its request, and a request is created — status Imported — for any OR number in neither file. Stock Transfer Lines: a line whose transfer is not in the register is held back. Opening stock: a name that is not an active User Master row is held back. Consumption: a call with no visit has one filed from the file's own Visit Date & Time — one per UCN — and rows whose call has no visit and no date are held back by name. Standard Complaint: matched on its Key, never renamed.

Then the confirmation: "Upload N rows into …? Rows are matched on …, so running this again corrects them rather than duplicating." — or, with no key, "⚠ This register has NO natural key — running it again will ADD N more rows, not correct these." Rows go up in batches (500; 300 for visit reports and sale or contract details; 2,000 for the history and opening-stock tables) with a running count, and the result reads "N rows written to …". After a Product Database or Party Master upload this device re-downloads its offline copy.

Restrictions & mandates

  • A load stops at the first batch the database refuses; batches already written stay: "… (row ~N) … (N written before it stopped.)"
  • A timeout adds "the database cancelled the batch. Re-run it: rows already written are updated, not duplicated."
  • Opening stock with no active User Master row at all is refused: "The User Master has no active users on this project, so every row would be held back. Load the User Master first."
  • The upload itself writes no Audit Log entry.

Flow 2 · Step 05

Bulk Report Mapping — card 0: references already in the register

Open: Bulk Report MappingFile a visit on a Field / installation / PM call

Visits loaded through Bulk Uploads keep the attachment cell as the file wrote it, so many hold an AppSheet path where a Drive link should be. 🔍 Survey the register counts the visits with a report, by shape, and how many still need converting. Set Convert up to … per pass (500 to start, 1 to 2,000), then 🔎 Resolve looks each file name up in Drive — in an optional folder first — and ⤵ Convert writes the links after a confirmation.

Only the link changes. The original reference goes into Source Ref unless that row already has one; the status, visit date, engineer and entry date are not touched. A file Drive cannot find, or finds twice, keeps its reference.

Restrictions & mandates

  • The Drive lookup needs the CallReg bridge set in Settings: "The Drive lookup needs the CallReg bridge — set its URL in Settings."
  • A role shown only its own and its team's visits is told the counts are "visits you can see".

Reads

  • Your CSV of recovered visits
  • The calls it names, by UCN or Call Number, and their visits

Flow 2 · Step 06

Bulk Report Mapping — steps 1 to 3: a sheet of recovered reports

File a visit on a Field / installation / PM call

1 · The sheet. Columns are found by name: UCN or Call Number (UCN wins), Visit Date, Engineer, Call Status and the attachment (Manual Report, Service Report, Attachment, File, Photo …); anything else is kept on the visit. A row finds its call by UCN, then by Call Number — never by serial or party. 2 · The attachments are looked up in Drive by file name; a name matching more than one file is left blank. 3 · What will be written shows every row with Will do:

skip — a completed visit on the call already has a report, or the row carries nothing to attach; 📎 attach — the call has a Solved - Report Completed visit with no report, so the link, its source reference, that status and the time of mapping are written onto it, and nothing else — not its entry date; ➕ file a new visit — the call has no completed visit, so one is filed with status Solved - Report Completed. ⤵ Attach N · file N asks to confirm, attaches first, then files.

  • Without an administrator or a visit key: "Loading recovered visit history needs a visit-report key for the Field, Installation or PM register."
  • MandateA row is held back for: "No call with that UCN or Call Number." · "… calls share that UCN." · "No usable visit date." · "No row id, and no call + visit date to derive one from."
  • PolicyEach visit written needs File a visit on that call's own register.

Flow 2 · Step 07

PM Bulk Upload — the month's PM batch

Open: PM Bulk UploadUpload PM calls in bulkCreate PM calls

⭳ Download template, then 📄 Choose CSV file. Set the Due month (this month to start; a past month to backfill), First registered at and the Gap between calls — pre-filled 00:30 on the 1st and 5 seconds for a fresh month, or 10 seconds after the latest call already in it, with 10-second gaps. The first eight calls are previewed: Call No, Party, Product, Serial, Engineer, Registered at, Added On, Type.

⬆️ Import N PM calls creates every row as a PM call, status Registered, dated the 1st of the due month, with today as Added On. A Call Number in the file is kept; a blank one is assigned. The UCN is always assigned by the system. Cover words are read as WGP / OGP / CMC / AMC. Unrecognised columns are kept on the call — including PM Due Date, which does not set the date.

  • MandateA row needs a party, a product or a serial; others are skipped as blank. None at all: "No usable rows — the file needs at least a Party / Product / Serial column. …"
  • PolicyEach call is created only for a holder of Create PM calls.
  • No key: importing the same file again creates its calls again.

Flow 3

Taking data out, and checking it

Everything here reads as you. Data Export downloads, the Solved Without a Report list and the visits Bulk Report Mapping surveys are all bounded by the same row rules as every other screen — so an empty or short result from a role that sees only its own and its team's records is a statement about that role, not about the register.

Reads

  • The names of the tables and views, with the database's own estimated row counts
  • The rows of each table you tick, as you may see them

Flow 3 · Step 03

Solved Without a Report — what to re-upload

Open: Solved Without a Report

Every call whose status reads Solved while its visit record is incomplete. The Missing column names every gap on the row: no visit at all · no visit date · entry date looks like an import stamp (N visits share it) — 25 or more visits entered at the same instant to the microsecond, the sign of a batch load — · no service report. The visit looked at is the latest entered, the same one the call's status comes from.

Chips filter by gap (a call with two gaps counts in both, so the chips add up to more than the calls); search by UCN, call number, party, product or serial. ⭳ Excel and ⭳ CSV download what is shown; the workbook has an About sheet with the scope and what each gap means.

Restrictions & mandates

  • PolicyThe rows are the calls you may see under the ordinary call rules; the page key restricts the screen, not the rows.
  • An empty list says "Every solved call has a dated visit and a service report behind it." only to a reader who sees every record; anyone else is told "No solved call that you can see is missing …"
  • A call reading Report pending is not listed (tested) — see Not yet in place.
  • Each download is recorded as report.solved_without_report.

Reads

  • Every profile, and what each device last reported

Flow 3 · Step 04

Device Cache Status — who can search offline

Open: Device Cache Status

One row per person per device, including everybody who has never reported: Person, Role, State, Device, App version, Machines and when downloaded, Customers and when downloaded, Complaints stored, Problem, Last reported. The State chips: Current (under 6 hours), Due a refresh (6-24 hours), Older than a day, No copy on the device, Never reported — judged on the older of the two downloads.

Each device reports after every download and on sign-out, so a device switched off shows its last report. Problem names a browser that will not keep a copy and the last download error.

Restrictions & mandates

  • FunctionWithout the page key the report itself is refused: "RBAC: the Device Cache Status report needs the mod:/device-cache permission." The page key is the whole right here.
  • TriggerA device can write only its own person's row; the person is taken from the sign-in.

Flow 4

How the system is set, and its own record

Admin Config holds the settings the rules read, each card with its own permission. Settings holds this browser's connections. Software Validation, the Tracker and Version History are the system's record of itself — what it must do and how that is proved, what is being worked on, and what changed.

Reads

  • The SLA targets
  • The Hotline desks — profiles with the Hotline role, and the chosen one
  • The frequent-failure settings

Flow 4 · Step 01

Admin Config — the settings the rules read

Open: Admin ConfigAdmin config (SLA targets, Call Registration desk, Frequent Failure rule)

SLA Targets — each rule's hours (shown in days where whole) and Active. The screen's built-in defaults are First visit 72 h, Call closure 120 h, Closure — call includes a spare 168 h, Closure — spare & not in CMC / WGP 240 h, Stores dispatch — from final approval 72 h; it saves only the rules you changed. They highlight open calls on track, due soon or breached on the Dashboard.

Call Registration — the Hotline desk: Calls are filed to one desk. Left empty, a new call goes to the single profile with the Hotline role, and to whoever registers it when there is none or more than one; the card says which applies now. Who actually registered each call is recorded separately and cannot be set.

Frequent Failure — the rule Review 2 applies. Rule 1: Failures needed (2 — counting the call under review) within a Window (months) (1), on the same equipment — with the same complaint while that box is ticked — or with the same part fitted in that machine. Rule 2: the same complaint on Serials needed (at least 2) different serials of one product within a Window (days) (30), while Rule 2 is in force. "Saved. It applies to reviews from here on — answers already recorded are unchanged."

Restrictions & mandates

  • Without the key the three cards are greyed: "Changing this needs “Admin config”." · "Changing these needs “Admin config”."
  • PolicyThe SLA targets and the settings table are written only by an administrator or a holder of Admin config.
  • An SLA target is at least 1 hour; Rule 2 needs at least 2 serials.

Reads

  • The Audit Mode setting and every change of it

Flow 4 · Step 02

Admin Config — Audit Mode

Switch Audit Mode on or off, and read its history

The badge reads ON or OFF. Type why, then Switch ON / Switch OFF. While it is on, a call's Update Party Details and Update Product Details are hidden and the database refuses them; nothing else behaves differently yet. Every change is kept with when, to, reason and by whom, and the table of changes is shown beneath.

Restrictions & mandates

  • Mandate"Give a reason — it is kept with the change." · Function"Changing Audit Mode needs a reason"
  • Function"RBAC: changing Audit Mode needs "Switch Audit Mode on or off""
  • FunctionWhile on: "Audit Mode is ON: a call's party and product details cannot be refreshed from the masters until an administrator turns it off."
  • PolicyThe history is readable by an administrator, View audit log or Switch Audit Mode; the card shows it only to the last.

Reads

  • CSV files — the table is worked out from their columns

Flow 4 · Step 03

Admin Config — Cover normalisation (legacy importer)

Load data through the Data Import panel

The card opens with "Loading a register? Use Bulk Uploads instead." It is kept for the four AppSheet sale / contract exports (Sale Entry, Warranty Sale Details, Contract Entry, Contract Details) and the Normalise cover step after them; it also recognises User Master and MRN files. Choose files, then Import N file(s). After a cover file it normalises automatically — values a machine line merely repeats from its entry go back to following the entry, and machine cover is refreshed — and Normalise cover runs that step again.

Restrictions & mandates

  • The card is not shown without its key.
  • No preview and no confirmation. The screen says: "Import into an empty table — re-importing duplicates rows, except the four sale / contract exports, which are matched on their own number and can be re-run safely."
  • PolicyEvery row still needs the table's own write right.

Reads

  • This browser's saved connections

Flow 4 · Step 04

Settings — this browser's connections

Open: SettingsChange the Settings page (connections, templates)Open the administration pages, read-only

Database Connection (Supabase): Project URL and anon public key, Test and Save. Google Sheet Connection: the CallReg Web App URL (ending /exec) and the Field Calls tab, Test and Save — the bridge Bulk Report Mapping uses for Drive lookups. Both are saved in this browser only, and Test saves what it tests.

Also: Design System Defaults (a description of how tables, forms and charts behave), Document Templates placeholders kept in this browser, and Reset Demo Data, which clears the old demo records held in this browser — "keeps your sign-in and theme". A person's own account, password and theme are on My Profile.

Restrictions & mandates

  • With neither key: "These settings are for administrators. Manage your own account, password and theme on the Profile page."
  • Read-only: "You can see how this app is set up, but not change it." The fields are greyed and Test, Save, the templates and Reset are not offered.

Reads

  • The validation package, held with the application
  • Recorded test results

Software Validation — the package

Open: Software ValidationRecord software validation results

The software validation package for the Field Service module, marked DRAFT — pending QA review & approval. Tabs include the Validation Plan, User and System Requirements, Requirements by Module, the Traceability Matrix, Data Flows (how a record moves from screen to screen, drawn from the package), the Defect Register, Risk Assessment and FMEA, Security, Data Integrity, Data Migration, Backup & Recovery, the Test Protocol (IQ / OQ / PQ) and the Summary Report. 🖨️ Print tab and 🖨️ Print full package.

On the Test Protocol a holder of the key records each test's result (Pass / Fail / N/A), actual result and tester; the summary counts what is recorded. It is not the servicing-process requirements, which are a separate document.

  • PolicyResults are written only with Record software validation results.

Flow 4 · Step 06

Tracker — the shared activity list

Open: TrackerDelete a Tracker item

+ Add an item adds one at the end. Each item has a title, detail, status (Open, In progress, Blocked, Done, Dropped), with whom, area and due date; every field saves when you click away. The number on a row is its position on the list you are looking at. Each row says who last changed it, when, and who raised it — stamped by the database. Done and Dropped are hidden until Show Done and Dropped is ticked.

Delete asks first: "Marking it Done or Dropped keeps it on the list — deleting removes it for everybody."

Restrictions & mandates

  • PolicyThe page key is the right to read, add and edit.
  • PolicyDeleting needs the page key and Delete a Tracker item; without it the button says "Deleting needs the “Delete a Tracker item” permission — mark it Done or Dropped instead".
  • CheckThe status can only be one of the five.
  • Adding and deleting are recorded in the Audit Log; edits are not.

Reads

  • The build this tab is running
  • The change log shipped with it

Flow 4 · Step 07

Version History

Open: Version History

Current build: Version, Build number, Build ID and when it was built. Change log: each release's version, date, summary and changes, newest first. Read only.

Separately, every tab checks for a newer build when it gains focus and every 5 minutes, and a banner offers ⟳ Update now. It names a version only when the version differs; otherwise it says "An update is out — this tab is running an earlier build of v…".

Restrictions & mandates

  • Nothing on this page changes anything.

The menu. An Administration entry is shown to a holder of its page key, of any Manage users key or of Open the administration pages, read-only; Tracker and Version History to holders of their page key. The page itself still opens only with its page key — otherwise "🔒 You don’t have access to this module. Ask an administrator to grant it in Roles & Permissions."

The records kept

  • Audit Log. Action, target, status, error and duration, with login, email and time stamped by the database; kept for the retention period (3,650 days unless changed).
  • The database trail. Before-and-after copies of rows written to fifteen quality tables, one event per bulk write over 150 rows; never purged; no screen reads it.
  • Audit Mode history. Every switch with its reason, who and when; the application cannot write or erase it.
  • Roles. Each role's stored permission list; a save is recorded as rbac.save naming the roles, an added role as rbac.role.add.
  • Export runs. Each scheduled run's tables, rows and outcome, readable and not editable.
  • Device reports. One row per person per device, the person stamped from the sign-in.
  • Tracker. Who raised each item and who last changed it, stamped by the database.
  • Validation results. One result per test.
  • System columns. Every table also records which login created and last changed each row, and when, written by the database.

Not yet in place

Stated here so nobody reads this page as describing them as done.

  • Solved Without a Report leaves out Report pending (D-090). Its About sheet says calls reading Solved - Report Pending appear too; a call with that status reads Report pending, which the list does not include (tested).
  • Admin config can switch Audit Mode with no reason and no history (D-088). A holder of Admin config can write the setting directly rather than through the switch; tested, the mode went ON and no change was recorded. The same holder can change the Audit Log retention period, which has no screen (tested).
  • An empty role is refused by the screen only (D-089). The database accepts one, and its people then get the Engineer's permissions (tested). A holder of Manage roles & permissions can also change the role they are on themselves (tested).
  • Workbook and ZIP downloads skip Export / download CSV (D-018, D-065) — the permission matrix, Solved Without a Report's Excel and Data Export. Data Export also writes no Audit Log entry, reads its pages in no fixed order, and stops at 200,000 rows a table without saying so (D-065).
  • Changes that leave no record (D-067): Bulk Uploads, the legacy importer, the SLA targets, the Hotline desk, the frequent-failure rule and a changed connection in Settings write no audit entry; a role save records only which roles, not what changed.
  • Bulk Uploads writes before you confirm (D-075): the spare-request stubs and the visits filed for consumption stay if you press Cancel — and a visit moves its call's status.
  • Loads that duplicate (D-071, D-038): the MRN Register and Stock Transfer Lines; the legacy importer's User Master and MRN files, with no preview; and PM Bulk Upload, which also accepts a call with no serial.
  • A re-test replaces the earlier validation result, keeping the first date (D-068).
  • The menu can offer an Administration page the person cannot open: any Manage users key, or the read-only key, shows every Administration entry, while each page asks for its own key.
  • Bulk Report Mapping counts an attach the database refused as attached (D-091): it does not check that a row was written.
